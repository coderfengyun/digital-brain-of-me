## 完整叙事

### 背景

Claude Code 已有 AutoMemory 功能：边聊边把项目信息写入 memory 文件，会话开始时注入上下文。但问题是——记忆只增不减，越堆越乱，memory.md 越来越长，反而降低了 AI 的响应质量。

### 核心故事

Anthropic 在 Claude Code 中推出实验功能 **AutoDream**。不同于 AutoMemory 的「随手记」，AutoDream 是一个后台运行的「整理员」：周期性拉起子 agent，回看历史会话，对记忆文件执行四个操作：

- **Merge（合并）**：将分散的相关记忆归并
- **Prune（修剪）**：删除过时、冗余的信息
- **Refresh（刷新）**：更新变化了的偏好和规则
- **Compact（压缩）**：把冗长描述浓缩为索引式要点

核心理念：**记忆应该是索引（index），不是信息倾倒（dump）**。

### 关键转折

作者发现 AutoDream 虽然是实验功能，但已经深入系统层——即使 `/dream` 命令返回 "unknown skill"，状态栏仍然显示 dreaming 并在后台运行。用自然语言说"运行你的 autodream"，Claude 嘴上说不认识，后台照样开始工作。这意味着 AutoDream 优先级已进入系统层，只是 UI/指令层还没统一。

### 结果与意义

AutoDream 带来三个核心价值：
1. **更少重复** — 不必反复交代背景、规则、偏好，记忆文件像干净的项目说明书
2. **更少膨胀** — 持续修剪 token 赘肉，更短更准更可控（更好的上下文 ≠ 更长的上下文）
3. **更好召回** — 球池比喻：100 个球找粉球，不是再加球，而是拿走蓝球。删掉无用信息，关键信息自然更醒目

触发机制（推测）：按时间（如每 12 小时）或按会话数（如 300 次）触发。只修改 md 记忆文件，不动代码。

## 批判性思考

### 1. 这篇文章最大的贡献是什么？

用「人类睡眠巩固记忆」的框架来理解 AutoDream，让技术功能变得直觉可理解。同时指出一个被忽视的问题：**上下文越多不等于越好**，AI 记忆管理的核心不是「记更多」而是「记更精」。

### 2. 什么地方你觉得证据不充分？

- 触发机制完全是推测（按时间/按会话数），作者自己也承认 "I don't know the exact implementation"
- 没有前后对比数据证明 AutoDream 确实提升了会话质量或减少了重复
- 仅基于一个视频演示展开分析，缺乏大规模用户验证

### 3. 如果你要基于这篇文章做下一步研究，会做什么？

在自己的 digital-brain 项目中实测 AutoDream（如果功能可用），对比整理前后的 memory 文件变化、会话启动效率和上下文命中率。另外值得关注的是：AutoDream 的整理逻辑是否与手动精心设计的 CLAUDE.md + memory 分层系统（如本项目的 progressive disclosure 设计）存在冲突或互补关系。

## 关键洞察

- **AutoDream = 人类睡眠巩固记忆的 AI 版本**：不在工作时打断你，而是在后台把碎片记忆整理成结构化长期记忆
- **更好的上下文 ≠ 更长的上下文**：记忆管理的核心是 pruning（修剪），而不是 accumulation（堆积）
- **记忆应该是索引，不是 dump**：理想的 memory.md 应该是「目录 + 要点 + 链接」，而不是聊天记录的翻版
- **功能已进入系统层但 UI 未就绪**：AutoDream 的优先级很高，实现先于文档，暗示 Anthropic 对此方向高度重视
