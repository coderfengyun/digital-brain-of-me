## 📖 核心叙事 (Narrative)

### 问题定义
OpenAI Realtime API 的核心约束是 **端到端延迟 < 0.3 秒**——从用户开口到听见 AI 回应。这 300ms 内要完成：音频采集 → 网络传输 → 服务器推理 → 语音生成 → 返回传输。留给网络层的预算极其有限。

### 方案选型（精读）
评估了三种方案：
1. **SFU**（行业默认）：为多方通话设计，管理编解码/录制/策略。OpenAI 场景是 1:1，这些能力是多余负担。
2. **TURN**：WebRTC 常用中继，但要求节点持有连接分配状态，不够轻量。
3. **Transceiver 模型**（最终选择）：在边缘终止 WebRTC 协议，转换为简单内部协议送给后端。状态集中，后端解耦。

### 架构核心（精读）
关键创新是把 transceiver 进一步拆成两层：

- **Relay**：纯 UDP 转发，无状态。只读包头 ufrag 标记做路由判断。内存中仅存转发映射 + 计数器 + 过期定时器。重启后自动重建。
- **Transceiver**：持有 ICE/DTLS/SRTP 和完整会话生命周期。是唯一的状态集中点。

这个分离解决了 K8s 环境下的端口耗尽问题——所有客户端连接同一组 relay 虚拟 IP:Port，relay 内部分发。

### 首包路由（精读）
用户第一个 STUN binding request 到达 relay 时，relay 没有任何上下文。解决方案：**在 ICE ufrag 中编码路由信息**。

流程：transceiver 生成 ufrag 时嵌入路由提示 → SDP answer 返回 relay 集群的虚拟 IP → 客户端首包 STUN 中带 ufrag → relay 解码得到目标 transceiver → 建立转发路径。

容灾：Redis 缓存 client IP:Port → transceiver 映射，relay 重启可快速恢复。

### 全球部署（扫读）
Global Relay：在全球各地部署相同的 relay 入口。用户数据包就近进入 OpenAI 内部骨干网。公网暴露面小且固定，安全和扩展更简单。

### Go 实现（扫读）
非常规选择 Go 而非 C++/Rust/kernel bypass。关键优化：SO_REUSEPORT 多进程共享端口、LockOSThread 绑核提高缓存命中、预分配缓冲区避免 GC。使用了 Pion 开源库。
