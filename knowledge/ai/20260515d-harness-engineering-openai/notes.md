## 完整叙事

### 叙事结构

```
约束: 零行人工代码构建真实产品
↓
发现: 早期进展慢 — 不是智能体能力不足，而是环境规范不明确
↓
核心转变: 工程师角色从"写代码"→"设计环境、明确意图、构建反馈回路"
├→ 让应用对智能体可读: git worktree + Chrome DevTools + 可观测性堆栈
├→ 情境管理: AGENTS.md 从百科全书→目录，渐进式披露
├→ 架构约束: 分层架构 + 自定义 linter + 结构测试，机械强制执行
└→ 熵管理: "黄金原则"编码 + 后台 Codex 任务自动清理
↓
结果: 5个月 → 100万行代码，3人团队 → 1500 PR，真实用户每日使用
↓
未解决: 长期架构连贯性、人类判断力如何编码、模型进化后系统如何演变
```

### 背景

OpenAI 内部一个小团队（最初 3 人，后扩展到 7 人）从 2025 年 8 月开始，自我施加了一个极端约束：**不手动编写任何代码**，完全由 Codex 智能体生成一个面向真实用户的内部产品。这不是技术 demo，而是有内部 DAU 和外部 Alpha 测试者的真实产品。

### 核心故事

**1. 工程师角色的根本重定义**

早期进展出乎意料地慢，但原因不是智能体能力不足，而是**环境的规范不够明确**。智能体缺乏工具、抽象层和内部结构来完成高级目标。工程师的核心工作变成了：

> "究竟还需要什么样的能力，我们又该如何让这个能力对智能体来说既清晰可读又可强制执行？"

这是深度优先的工作方式：拆解目标为构建模块 → 提示智能体构建 → 用产出解锁更复杂任务。当事情不顺利时，答案不是"再努力一点"，而是改善环境。

**2. 让一切对智能体可读**

团队系统性地扩展了智能体的"感知能力"：
- **UI 可读**: 应用按 git worktree 启动，接入 Chrome DevTools 协议，智能体可以复现 bug、验证修复、推理 UI 行为
- **可观测性可读**: 本地临时可观测性堆栈（日志/指标/追踪），智能体可用 LogQL/PromQL 查询。让"确保启动在 800ms 内"这样的提示成为可能
- 单次 Codex 运行可持续工作超过 6 小时（通常在人类睡眠时间）

**3. 情境管理：地图而非百科全书**

这是文章的核心洞察之一。团队尝试过"一个大型 AGENTS.md"方案，失败了。四个原因：
- **情境是稀缺资源** — 巨大指令文件挤掉了任务和代码的空间
- **过多指导反而无效** — 当一切都"重要"时，智能体做局部模式匹配而非有意导航
- **立即腐烂** — 庞杂手册变成陈旧规则的坟场
- **难以核实** — 单个 blob 无法做机械检查

解决方案：AGENTS.md 变成约 100 行的**目录/地图**，指向 `docs/` 中结构化的知识库。这实现了**渐进式披露**（progressive disclosure）。专职 linter、CI 作业和"doc-gardening"智能体保持知识库的更新。

**4. 架构约束作为倍增器**

智能体在严格边界和可预测结构中最高效。团队的做法：
- 每个业务域固定分层：Types → Config → Repo → Service → Runtime → UI
- 横切关注点通过单一接口 Providers 进入
- 自定义 linter（由 Codex 生成）机械强制执行，lint 错误信息中注入修复指令
- 要求"在边界处解析数据形状"（parse, don't validate），但不指定具体库

关键原则：**在中央层面强制执行边界，在本地层面允许自主权**。

**5. 熵与垃圾收集**

智能体会复现代码库中已有的模式，包括不够理想的。早期每周五手动清理"AI 残渣"不可扩展。

解决方案："黄金原则"编码到仓库 + 后台 Codex 任务定期扫描偏差、更新质量等级、发起重构 PR。技术债务像高息贷款一样持续小额偿还，而非累积后一次性解决。

### 关键转折

从"人类写代码，智能体辅助"到"人类设计环境，智能体执行一切"的范式转换。关键突破点是团队意识到**智能体遇到困难是环境问题而非能力问题**。

### 结果与意义

- 5 个月从零到百万行代码
- 3 人团队完成 1500 PR（人均 3.5 PR/天），扩展到 7 人后吞吐量反而增加
- 智能体可端到端驱动新功能（复现 bug → 修复 → 验证 → PR → 合并）
- 几乎所有代码审查由智能体对智能体完成

## 批判性思考

### 1. 这篇文章最大的盲区是什么？

**选择偏差与生存者偏差**。这是 OpenAI 自己的团队、用 OpenAI 自己的产品（Codex）构建的项目。团队成员对模型的理解、对产品路线图的内部知识、以及可能获得的模型定制/优先支持，都是外部团队无法复现的条件。文章末尾承认"此行为不应在没有类似投入的情况下假定它可以泛化"，但这个 caveat 被大量激动人心的数字淹没了。

### 2. 如果核心论点是对的，有什么非显而易见的推论？

如果"harness engineering"确实是未来的核心范式，那么**软件工程的核心技能将从"编写代码"转向"设计约束系统"**。这意味着：
- 最有价值的工程师是那些能够设计好的架构边界、写好的 linter 规则、构建好的反馈回路的人 — 更像系统架构师而非实现者
- "品味"（taste）变成了一种可编码的组织资产 — 谁能更好地将隐性知识转化为机械可执行的规则，谁就有竞争优势
- 代码审查的重点从"这段代码对不对"变成"这个约束系统是否足够完备"

### 3. 与我自己的 digital-brain 系统有什么共鸣？

这篇文章描述的 context engineering 实践与我的 digital-brain 系统高度一致：
- **渐进式披露** = CLAUDE.md 作为路由索引 → 模块入口 README → 数据文件
- **代码仓库作为记录系统** = flat-file relational model，一切情境都在仓库内
- **AGENTS.md 作为目录而非百科全书** = CLAUDE.md 的 Module Navigation 表只做路由，不展开处理步骤
- **doc-gardening 智能体** = 我需要考虑是否也引入类似的自动化维护

关键区别：他们有自定义 linter 机械强制执行约束，而我的系统目前主要依靠 skill 指令的"软约束"。这是一个值得改进的方向。

## 关键洞察

- **给智能体一张地图，而非一本说明书** — 情境是稀缺资源，渐进式披露比信息倾泻更有效
- **智能体遇到困难是环境问题而非能力问题** — 解决方案永远不是"再努力一点"，而是改善工具、抽象和约束
- **品味可以编码** — 通过 linter、结构测试和"黄金原则"将人类判断力转化为机械可执行的规则
- **架构约束对智能体是倍增器而非束缚** — 在以人为本的工作流中显得迂腐的规则，在智能体工作流中变成了效率杠杆
- **熵管理需要自动化** — 智能体会放大代码库中的模式（包括坏模式），需要持续的"垃圾回收"机制
- **纠错成本低于等待成本** — 在高吞吐量智能体系统中，快速合并+快速修复优于严格的合并门控
