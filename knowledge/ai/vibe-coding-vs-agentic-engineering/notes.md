## 📖 完整叙事（中文翻译 + 结构化）

### 一、"从未如此落后"——转折发生在 12 月

**Stephanie 开场**：去年 Karpathy 发明了"vibe coding"这个词，但最近几个月他说出了更令人震惊的话——"我作为程序员从未感到如此落后"。

**Karpathy**：两者兼有——既兴奋又不安。过去一年我一直在用 agentic 工具写代码，它能写出不错的代码块，偶尔出错需要手动修改。**12 月是一个明确的转折点**——我在休假，有更多时间尝试。我注意到最新模型产出的代码就是对的，我要求更多，还是对的。我记不起上次修正它是什么时候了。然后我就越来越信任系统——然后我就在 vibe coding 了。

这是一个非常鲜明的过渡。很多人去年对 AI 的体验还停留在 ChatGPT 聊天机器人阶段，但**你真的需要在 12 月之后重新审视——agentic coherent workflow 真正开始工作了**。之后我就掉进了无限副项目的兔子洞，我的副项目文件夹里塞满了各种东西。

### 二、Software 3.0——一个全新的计算范式

**Stephanie**：你谈过很多 LLM 作为新型计算机的想法——不只是更好的软件，而是全新的计算范式。Software 1.0 是显式规则，2.0 是学习权重，3.0 是这个。如果这是真的，一个团队在真正相信这一点的那天会怎样不同地构建产品？

**Karpathy**：
- **Software 1.0**：我写代码
- **Software 2.0**：我通过创建数据集和训练神经网络来编程
- **Software 3.0**：编程变成了 prompting。**上下文窗口中的内容就是你对 LLM 这个解释器的操控杆**

**例子 1：OpenClaw 安装**

传统做法是写 bash 脚本来安装，脚本为了兼容各种平台会膨胀得极其复杂。但 OpenClaw 的安装方式是：复制一段文本给你的 agent。Agent 有自己的智能，会查看你的环境、你的电脑，执行智能操作让它工作起来并在循环中调试。这就是 Software 3.0 范式——**给 agent 的那段文本就是编程范式本身**。

**例子 2：MenuGen**

我做了一个 app：拍餐厅菜单照片 → 上传 → 重新渲染菜单并给每道菜配图。我写了代码，部署在 Vercel 上。然后我看到了 Software 3.0 版本——**直接把照片给 Gemini，说"用 NanoBanana 把菜品图片叠加到菜单上"**。它直接返回了一张图片，就是我拍的菜单照片，但每道菜旁边渲染了对应的图片。

关键不只是"现有工作变快了"，而是**全新的事物成为可能**。比如 LLM knowledge base 项目——让 LLM 为你的组织、个人创建 Wiki。这不是一个程序，以前不存在能"基于一堆事实创建知识库"的代码。现在你可以把文档重新编译、重组，创造出新的东西。**这比"加速现有工作"更令人兴奋。**

### 三、神经网络将成为宿主进程

**Stephanie**：如果继续外推——就像 90 年代建网站、2010 年代做 App——2026 年的等价物是什么？什么东西现在还没建出来但将来回头看会觉得显而易见？

**Karpathy**：延续 MenuGen 的例子——很多代码不应该存在，应该由神经网络完成大部分工作。想象一个设备：输入原始视频/音频到神经网络，用 diffusion 渲染出当下独一无二的 UI。

在 1950-60 年代，计算机到底应该像计算器还是像神经网络，并不明显。我们走了计算器路线，建立了经典计算。**现在神经网络还跑在经典计算机上（虚拟化的），但未来会反转——神经网络成为宿主进程，CPU 退化为确定性工具调用的协处理器。**

神经网络计算将占据 FLOPS 的绝对主导。想象一个很陌生的世界：神经网络做大部分重活，tool use 只是处理确定性任务的历史残留物。

### 四、可验证性与锯齿智能（Jaggedness）

**Stephanie**：AI 会更快地自动化那些输出可以被验证的领域。如果这个框架正确，哪些工作会比人们预期的更快被变革？

**Karpathy**：传统计算机能轻松自动化你能在代码中指定的东西。LLM 能轻松自动化你能验证的东西。因为前沿实验室在训练 LLM 时，本质上是巨大的强化学习环境，给它们验证奖励。这造就了**锯齿状实体**——在可验证领域（数学、代码）能力巅峰，在其他领域则粗糙得多。

**锯齿性的终极例子**：以前是"strawberry 有几个字母"（模型答错了）。现在的例子是：我要去洗车，洗车店在 50 米外，应该开车还是走路？最先进的模型会告诉你走路（因为很近）。**同一个模型能重构 10 万行代码、发现零日漏洞——却告诉你走 50 米去洗车。这太疯狂了。**

锯齿性说明两件事：
1. 可能有些东西不太对
2. **你需要留在循环中**，把它们当工具用，保持对它们行为的关注

为什么会锯齿？是**"可验证性" + "实验室关注度"**的组合。GPT-3.5 到 GPT-4，国际象棋能力巨幅提升不是自然演进——是因为有人往预训练数据里放了大量象棋数据。

**对创始人的启示**：如果你在一个可验证的领域，即使大实验室没直接关注它，你也可以自己创建 RL 环境做微调，这技术就是能 work 的。存在一些非常有价值的 RL 环境还没被开发（Karpathy 暗示但没透露具体领域）。

最终，几乎所有事情都可以在某种程度上变得可验证——甚至写作也可以通过 LLM 评审团来验证。**所以最终一切都是可自动化的**。

### 五、Vibe Coding vs Agentic Engineering

**Stephanie**：去年你创造了 vibe coding 这个词，今天的世界感觉更严肃——更像 agentic engineering。两者有什么区别？

**Karpathy**：
- **Vibe Coding 提升下限**：每个人都能用 AI 编写软件，这很棒
- **Agentic Engineering 提升上限**：保持专业软件的质量标准——不能因为 vibe coding 就引入漏洞。你仍然对软件负责，但能不能更快？答案是可以，但怎么正确地做？

我称之为 agentic engineering 是因为这确实是一门工程学科：你有这些 agent——它们是尖刺状实体，有些脆弱、有些随机性，但极其强大。**如何协调它们更快运作而不牺牲质量标准？做好这件事就是 agentic engineering。**

以前人们说"10x 工程师"。现在这个倍数放大了很多。**10x 不是你能获得的加速。擅长这个的人远超 10x。**

### 六、招聘范式变革

**Stephanie**：如果我们观察两个人用 Claude Code / Codex 编程——一个平庸、一个完全 AI-native——区别是什么？

**Karpathy**：就是充分利用可用工具的所有功能，投入自己的环境配置。就像以前工程师要精通 Vim 或 VS Code，现在要精通 Claude Code、Codex 等。

**关于招聘**：大多数人还没有为 agentic engineering 能力重构招聘流程。如果你还在出算法题，那就是旧范式。

**新的招聘应该是**：给一个真正的大项目，比如写一个 Twitter 克隆，让它做得好、做得安全，让 agent 模拟用户活动。然后**我用 10 个 Codex 去尝试攻破你部署的网站——它们不应该能攻破**。

### 七、人类不可替代的技能——品味、判断力、Spec 设计

**Stephanie**：什么人类技能变得更有价值？

**Karpathy**：目前 agent 还是实习生级别的实体。你仍然需要掌控美学、判断力、品味和监督。

**例子：MenuGen 的用户 ID bug**——用 Google 账号注册、用 Stripe 付费，两者都有邮箱。Agent 用邮箱来关联消费记录，但用户可能用不同邮箱——资金就对不上了。这种错误 agent 还是会犯的。为什么会用邮箱来交叉关联？应该用唯一用户 ID。

所以**人类要负责 spec、plan 的设计**。你要和 agent 一起设计非常详细的规范，然后让 agent 来填充细节。

**我已经忘了 PyTorch 和 NumPy 的 API 细节**——keepdims 还是 axis，reshape 还是 permute——不需要记了，这是实习生（agent）的事，它们记忆力很好。但你仍然需要知道底层 tensor 有 view 和 storage 的区别，不要不必要地复制内存。**你负责品味、工程设计——agent 填充实现细节。**

**关于 AI 生成代码的质量**：看代码有时会心脏病发作——臃肿、大量复制粘贴、抽象尴尬脆弱。能跑，但真的很 gross。我试过让模型简化 microGPT 项目——**模型做不到。你让它"再简化"——它做不到。你感觉自己在 RL 电路之外，像拔牙一样痛苦。**

这不是根本性限制，只是实验室还没做到。

### 八、动物 vs 幽灵——理解 AI 的本质

**Stephanie**：你写过一篇很有启发性的文章——"我们不是在建造动物，而是在召唤幽灵"。这些是被数据和奖励函数塑造的锯齿智能，没有内在动机、好奇心、赋能感。这个框架为什么重要？

**Karpathy**：我写这个是因为我想搞清楚这些东西到底是什么。如果你有一个好的模型来理解它们是什么/不是什么，你就能更好地使用它们。

关键认知：你冲它喊叫不会让它工作得更好或更差——它没有任何反应。它就是统计模拟电路，底层是预训练（统计），上面叠了 RL。**这更多是一种心态——知道什么可能有用、什么可能没用、怎么修改它。** 我没有"五条明确的结论"，更多是保持怀疑并随时间摸索。

### 九、Agent-Native 世界

**Stephanie**：当 agent 不只是聊天，而是有真实权限、本地上下文、能代表你行动——那个世界是什么样的？

**Karpathy**：一切都还是为人类写的，需要被改写。我用各种框架/库，文档仍然是面向人类的。这是我最大的吐槽——**为什么还在告诉"我"该做什么？我不想做任何事。给我一段可以复制给 agent 的东西！**

大家都在思考：如何把工作分解为世界的 sensor 和 actuator？如何让一切变成 agent-native——先给 agent 描述，再围绕数据结构做大量自动化。

比如 MenuGen 的痛苦不是写代码，而是**部署到 Vercel——要配置各种服务、设置菜单、配置 DNS**。理想状态是给一个 prompt，什么都不碰就部署到互联网上了。

最终我们会走向**agent 代表个人和组织的世界**——我的 agent 和你的 agent 商量会议细节。

### 十、教育——"你可以外包思考，但不能外包理解"

**Stephanie**：当智能变得廉价，什么仍然值得深度学习？

**Karpathy**：最近有条推文让我每隔一天就在想——**"You can outsource your thinking, but you can't outsource your understanding."**（你可以外包你的思考，但不能外包你的理解。）

我仍然是系统的一部分，信息仍然需要进入我的大脑。我感觉自己正在成为瓶颈——知道我们要建什么、为什么值得做、如何指挥 agent。**某些东西必须指导思考和处理，这仍然根本性地受限于理解力。**

这就是为什么我对 knowledge base 工具这么兴奋——这是我处理信息的方式。每当我看到信息的不同投影（projection），我总觉得获得了洞察。我读文章时有个 wiki 在持续构建，我喜欢问各种问题。

这些都是**增强理解力的工具**——如果你理解得不够，你就不可能成为好的 director。Agent 目前确实不擅长理解，**你仍然是唯一负责理解的人**。

## 🧠 批判性思考

### 1. 这个框架的边界在哪里？

Karpathy 的"提升下限 vs 提升上限"框架精炼有力，但隐含假设是**质量标准可以被清晰定义**。现实中，很多软件的"质量"是模糊的、演化的、政治性的。当整个行业都在 vibe code 时，"质量标准"本身可能会下降——就像 web 开发质量标准在 WordPress 时代的演变。

### 2. "一切都可自动化"与"理解不可外包"的张力

Karpathy 一方面说"最终一切都可自动化"，另一方面又说"理解不能外包"。如果 AI 最终也能理解，那人类价值的最后壁垒在哪里？他自己也承认"期待几年后回来看看是否被完全自动化出循环"——这是一种诚实的不确定性。

### 3. 锯齿智能的实践意义

"洗车 50 米该走还是开车"这个例子极其有力。它暗示的实践准则是：**在每个新场景使用 AI 前，你需要实证测试它是否在该领域的"RL 电路内"**——不能假设"能重构代码 = 能做常识推理"。这对任何想用 AI 构建产品的人都是关键的第一性原理。
