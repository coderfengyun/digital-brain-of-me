## AI 总结

### 00:25 — 开场与背景

对话开始时有人提议做个介绍，但很快转向了任务分配问题。明显存在责任推诿，一位参与者明确拒绝承担录音任务，强调这不是他的义务。潜台词是团队分工不明确，导致有人对重复性工作产生抵触情绪。

### 02:41 — 迁移背景与方案

团队正在紧急迁移到客套平台，因为 GPT Pro 账户即将在一周内失效。他们计划保留本地 APP 来处理客套不支持的流程，但整体操作逻辑不变。

迁移的核心优势在于 Code S 的集成：新建课程等操作会直接走 Code S 逻辑，资料预置和文件夹创建都自动化了。演示显示点击链接就能直接进入工作文件夹，比旧流程节省了手动建文件夹的步骤。

### 05:12 — 迁移时间节点与 Codex 介绍

关键时间节点是 **7月1日前**完成迁移，届时会统一处理插件转移和版本适配问题。技术负责人明确表示 APP 在签约 Codex 前将暂停迭代。

Codex 相比现有系统的主要优势：
- 插件可视化管理
- 自动无感升级功能
- 纯 Agent 模式运行（无 IDE 模式）

迁移流程已规划完成，用户端无需额外操作，团队会提供详细使用指南。

### 07:10 — 新工具使用体验

新工具 UI 更直观但功能有所限制：
- 查看文件需要每次点击按钮
- 不能直接编辑文件内容，只能通过外部编辑器修改（open in cursor/editor）
- 没有 IDE 模式，直接进入 agent 模式

### 09:12 — 配置与账号问题

- Codex 通过公司额度，下载需查收邮件
- 使用 GPT Pro 个人账号需要把「开头」（Openhead 类工具）取消掉，因为两者走的路径不同
- 本地助手的作用：将流量导向公司网关平台，而非 OpenAI 官方网关

### 11:35 — 账号切换与成本

个人订阅账号与公司平台账号存在绑定冲突，必须手动切换。有人提到个人 GPT 账号额度消耗极快，两天就用掉 180 美元。

### 13:40 — workspace 迁移技术流程

迁移方案存在两种选择：open in cursor 或 open in codex，需要尽快测试发版。时间压力大，「7月1日」是硬截止。

### 15:51 — 题库 pipeline 优化

团队优化题库 pipeline，遇到三个问题：
1. 题目答案错误
2. 归类混乱
3. 题量不足

优化方向：完善前置知识图谱 + 明确抓取规范。

### 18:25 — 选题流程与题库建设

- 双题源策略：教研云 + 金融网
- 限制年级、教材版本和题目类型确保质量
- 最低题量要求从 8 道调整为 4 道

### 20:32 — 题库抓取自动化

系统已实现从题库自动筛选 8 道题的功能，但最终用题仍需人工确认。发现异常题（约 20-30 道）可能倒逼知识图谱扩展新题型。

### 22:33 — 人力投入

每个主题（含 4-5 知识点）需 2.5-3 小时处理，其中人工必须介入题型分流和质量把关两个环节。

### 25:10 — 流程优化

系统可 24 小时连续运行，只需上班时间集中检查分流结果。多账号并行处理不受限制。

### 27:35 — 成本与数据量

- 一个中文主题的抓取成本大约 80 美元以上
- 五年级上学期有 17 个主题，奥数 7 个
- 评测机目前只有 6 个 skill，数据不足

### 29:38 — 课件系统优化

- 设计介入时机滞后问题明确
- 图片替换和教具优化仍是痛点
- 计划利用 Modify 设计平台 + MCP 服务实现设计元素快速提取和迭代

### 31:40 — 设计工作台方案

通过设计工作台实现轻量级图片素材替换，教具优化通过解析设计稿链接提取元素参数，低门槛复用现有教学代码，在现有课件系统中逐步集成组件库。

### 34:11 — 设计流程割裂问题

设计完成后需经评估、设计出稿、前端修改等多环节，设计团队反馈时间窗口被严重压缩。希望设计能通过工作台直接调整 motif 规范，避免反复传递损耗。

### 38:40 — 设计规范进度

- 视觉设计规范已有初稿，正在转化为 md 文件
- 交互设计规范更复杂，需逐步建立组件库
- 情景图规范已在使用，教具规范因暑期课延误尚未落地
- 计划用「牛吃草」案例进行规范前后生产对比测试

### 40:39 — 方案拆分

建议将设计系统拆分为独立方案，当前会议仅解决后置调优环节。关于课程设计平台，整合进现有课件系统还是开发独立平台尚未达成共识。

### 43:15 — 教具设计自动化

设计老师可以直接上传图片并替换，无需额外部署。通过链接解析直接提取设计参数，确认后即可触发自动化生产流程。

### 45:19 — 教具修改职责划分

核心矛盾：设计介入的时机选择。有人认为应在教具生产流程稳定后介入，当前做法可能导致多人协作混乱。提出设计系统看板台统一管理素材。

### 47:43 — 信息传递问题

设计修改与教具生产之间的信息断层：设计同事需要明确知道教具使用场景才能有效修改，当前流程依赖文字 comment 间接传递，存在信息损耗风险。

### 49:52 — 异步协作痛点

多人同时修改导致权限混乱和效率低下。提出阶段锁死机制，但异步多轮反馈的延迟问题依然无解。

### 52:11 — 代码修改权限划分

讨论 UI 和逻辑层的隔离问题。技术方案：通过 vlab 流水线实现快速验证，非实时编辑，最终产物仍需经过常规流程。

### 54:10 — 设计修改边界

设计修改主要限于视觉和布局，功能交互已由产品前置确定。提交修改后通过流水线快速验证更新，而非直接编辑最终产物。

### 56:29 — 修改方式分歧

是否直接在真实教具上修改，还是通过副本修改后合并。双方对「真实修改」的理解存在差异。

### 58:31 — 解耦方案达成共识

设计同学可以直接修改课件系统引用的教具产物，隔离式开发模式获得团队一致认可。流程明确分为：产品准出 → 视觉交互两个阶段。

### 1:00:43 — 板书系统架构

确立结构层（元素组成）和时序层（组件交互逻辑）的分层设计思路。

### 1:02:50 — 课件系统与板书系统协同

底层结构层/时序层强制保持一致，组件层/批注层可灵活调整。课件系统为迭代主体，板书系统处于被动适配状态。

### 1:04:50 — 设计权限边界

设计师只能调整教具和图片等视觉元素，不能触碰教学逻辑、prompt 或板书结构等核心内容。

### 1:07:19 — 栅格布局优化

八等分栅格在处理单行文字时效果良好，但遇到两行文字就会产生空白区域。新共识：允许合理留白，转向更灵活的版面规范。去除边框和底色，向更简洁的视觉呈现迈进。

### 1:09:26 — 列切分+行自适应布局

采用列切分+行自适应的混合布局：固定列数（如 3-4 列），行高根据内容自适应调整。典型案例：三列布局，题面占全宽，线段图占 2/3 宽，关键算式占 1/3 宽。

### 1:12:04 — Slots 概念

在行列布局基础上引入 slots 概念标记位置关系，处理教具与文本框的堆叠排列，以及同一位置多个组件覆盖/替换的情况。

### 1:14:11 — 重叠组件封装

将特殊重叠场景封装成独立组件，通过动作顺序（show/head）控制展示流程。

### 1:16:15 — 组件切换逻辑

讨论 hide/show 直接操作 vs 互斥组件预置方案。「对老师要求高」是核心顾虑，尚未形成明确结论。

### 1:24:50 — 自适应布局矛盾

动态内容与静态预设的冲突：设计阶段 BC 区域预设一行文字，实际授课时 C 区可能需要更多行，纯自适应方案无法预判真实教学场景的内容量差异。

### 1:29:10 — 折中方案

大模型首版生成自适应布局后，老师保留调整高度的权限，但不必纠结具体行列数。

### 1:33:58 — 简化方案

只定义元素间的行关系而非具体尺寸。强调「老师理解不了的东西做不好」，设计应基于实际存在的内容，反对过度预设未使用的空间。

### 1:38:46 — 版本管理流程

技术团队认为 build 即生成可交付版本，教学层坚持需要真实课堂验证才敢 release，两者存在根本分歧。两个议题临时叫停转为专项讨论。

### 1:41:00 — 发布标准

技术方：发布即交付；教学方：需真实课堂验证。教具可例外。关于多版本管理：要么确定唯一可靠版本，要么重新命名区分。

### 1:43:07 — 备课系统准出

只要备课系统准出就不干涉具体流程，风险管控责任下放给下游环节。

### 1:45:12 — AB 测试

当前无需强制支持双版本，但方案需具备扩展能力。若需测试，可通过线下 YAML 文件自行操作。

### 1:47:34 — 课设 skill

当前版本生成的备课 MD 文档质量不佳，导致教师只能依赖课件系统手动制作 PPT。核心痛点：自动化产出与人工精调之间的效率断层。

### 1:49:34 — 课设与课件分工

- **课设阶段**：搭建教学骨架（教学目标、学生基础分析、教学素材选择、认知难点梳理）
- **课件阶段**：基于课设成果细化话术、动作设计等执行层内容

### 1:51:45 — 新工具演示
