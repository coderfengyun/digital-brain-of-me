# 安全地为大型代码库建立索引

**类型**: 方法

---

## 📖 核心叙事 (Narrative)

### 一句话概括
> Cursor 通过 Merkle tree + simhash 索引复用 + 访问证明机制，让团队新成员能在几秒内安全地获得大型代码库的语义搜索能力，而非从头等待数小时。

### 叙事结构

```
问题: 大型代码库（数万文件）的语义搜索索引构建耗时数小时，80% 完成前无法使用
↓
观察: 同一组织内不同用户的代码库克隆版本平均相似度达 92%
↓
假设: 如果能安全复用已有索引，就无需每个用户从头构建
↓
方法: 三层架构——① Merkle tree 增量同步 ② simhash 相似索引查找 ③ 访问证明防泄漏
↓
验证: p50 首次查询时间从 7.87s→525ms, p90 从 2.82min→1.87s, p99 从 4.03h→21s
↓
结论: 团队规模越大、仓库越大，索引复用的收益越显著
```

## 📊 数据证据层 (Evidence)

| 论点 | 创新点 | 支撑数据 | 数据来源 | 说服力评估 |
|------|--------|----------|----------|------------|
| 语义搜索能显著提升 agent 性能 | 将语义搜索作为 agent 核心能力 | 平均准确率提升 12.5%，代码修改留存率更高 | Cursor 内部评估 ([semsearch blog](https://cursor.com/blog/semsearch)) | ⭐⭐⭐ 强——有对照评估数据 |
| Merkle tree 大幅减少同步数据量 | 用密码学树结构做增量差异检测 | **例子**: 5 万文件的工作区，文件名+SHA-256 哈希约 3.2MB；有 Merkle tree 后只需遍历不同分支，而非全量传输 | 文中估算 | ⭐⭐ 中——只给了一个估算值，没有实际传输量对比 |
| 团队内代码库高度相似，可复用索引 | simhash + 向量数据库查找最佳匹配索引 | 同组织内代码库平均相似度 92% | Cursor 内部统计 | ⭐⭐⭐ 强——92% 这个数字直接支撑了复用的可行性 |
| 索引复用后首次查询时间大幅缩短 | 后台拷贝索引 + 即时查询已有索引 | p50: 7.87s→525ms (15x), p90: 2.82min→1.87s (90x), p99: 4.03h→21s (690x) | Cursor 生产数据 | ⭐⭐⭐ 强——多分位数据、改进幅度巨大 |
| 访问证明防止跨用户代码泄漏 | 复用 Merkle tree 哈希作为文件拥有权证明 | **例子**: 客户端上传 Merkle tree → 服务器存为内容证明 → 搜索时比对哈希 → 客户端无法证明拥有的文件结果被丢弃 | 系统设计描述 | ⭐⭐ 中——设计合理，但无攻击测试或安全审计数据 |

## 🤔 批判性思考 (Critical Thinking)

| 问题 | 分析 |
|------|------|
| 核心假设及失效场景 | 假设: 团队成员的代码库高度相似（92%）。<br>失效场景: ① mono-repo 中不同团队只 checkout 部分目录（sparse checkout），相似度可能远低于 92% ② 长期未更新的本地分支与团队版本差异巨大 ③ fork 出去的独立项目 |
| 关键局限 | - 访问证明只验证「你有这个文件的哈希」，但如果攻击者获得了文件路径+哈希（如从 git log），理论上可伪造证明<br>- simhash 的阈值选择未公开，过高会错过可用索引，过低可能复用不相关索引<br>- 文中未讨论 embedding 模型更新时如何处理已缓存的旧 embeddings |
| 实验充分性 | 缺失验证: ① 没有安全性的红队测试结果 ② 没有 simhash 匹配精度的评估（false positive/negative rate） ③ 没有与其他增量索引方案的对比（如 git diff-based） |
