# Skill 调用 Skill：Skills 的乐高式组合

**类型**: 叙事

---

## 完整叙事

### 背景

作者（宝玉AI）在开发漫画生成 Skill 时遇到一个问题：Skill 需要画图能力，但用户可能安装了不同的画图 Skill（Nano Banana Pro、Midjourney 等）。是否需要硬编码调用哪个？

### 核心故事

答案是不需要。Claude Code 的 Skills 系统有一个关键设计：**Agent 启动时预加载所有已安装 Skill 的名称和描述**。因此 Skill 之间可以基于能力描述进行松耦合调用——你只描述"需要什么能力"（如"帮我画张图"），Claude 在运行时自动匹配可用的 Skill。

实现方式是在 SKILL.md 中写：
> Check available image generation skills. If multiple skills available, ask user preference.

Claude 还能动态适配目标 Skill 的能力差异（支持参考图就传图，只支持文本就传描述）。

### 结果与意义

这种松耦合带来四个好处：可替换、可扩展、低维护、用户自主。Skills 成为真正的乐高积木——独立模块，自由组合。

---

## 关键洞察

- **能力描述 > 直接依赖**：Skill 间调用不是通过 import/API 调用，而是通过自然语言描述需要的能力，让 Agent 在运行时动态匹配。这本质上是**依赖注入**的 AI-native 实现
- **启动即感知**：Agent 启动时预加载全部 Skill 元信息，这是松耦合能工作的基础设施前提
- **与 digital-brain 的关联**：我们的 skill.md 路由表设计和这个思路一致——模块只描述自己的能力，上层（skill.md）做路由匹配。但我们目前是静态路由，这篇文章展示的是动态发现模式，值得借鉴

## 批判性思考

| 问题 | 分析 |
|------|------|
| 可靠性 | 基于自然语言匹配的松耦合在能力描述模糊时可能误匹配。"帮我画张图"足够明确，但更复杂的能力需求（如"帮我做数据可视化"）可能匹配到不合适的 Skill |
| 篇幅与深度 | 文章非常短，只展示了一个简单案例（画图），未讨论失败场景、冲突处理、Skill 版本兼容性等工程问题 |
| 适用范围 | 这个模式在能力边界清晰（画图、翻译等）时工作良好，但在能力重叠或需要精确控制时可能不够 |
